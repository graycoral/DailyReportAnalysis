# 데일리 리포트 작성·게시 규칙

리포트를 생성해 GitHub에 올리는 쪽(ChatGPT 일일 작업)이 지켜야 할 규칙입니다. 기준은 기존 발송본 중 가장 정리된 형태인 `data/reports/2026-10-14/autonomous_driving_daily_2026-10-14.md`입니다. 이 규칙을 지키면 GitHub Actions가 나머지(catalog·DB 생성, 커밋)를 자동으로 처리하고, 다음날 08:00 KST에 모든 사용자 화면에 반영됩니다.

## 1. 어디에 무엇을 올리나

```
data/reports/YYYY-MM-DD/autonomous_driving_daily_YYYY-MM-DD.md     (필수)
data/reports/YYYY-MM-DD/autonomous_driving_daily_YYYY-MM-DD.pptx   (선택)
```

- 브랜치는 `main`. 폴더 이름의 날짜가 리포트 ID이자 보고일이 됩니다. 한 폴더에 MD는 하나만 둡니다.
- 하루에 한 건. 같은 날짜를 다시 push하면 본문·첨부가 교체되고 catalog에서 손으로 고친 요약·태그·출처는 유지됩니다.
- 08:00 KST 전에 push가 끝나야 그날 아침 갱신에 포함됩니다.
- 파일 인코딩은 UTF-8, 줄바꿈은 LF.

## 2. 머리말 (front matter)

파일 맨 위에 아래 블록을 둡니다. `info` 한 줄이 **리포트 제목**이 됩니다.

```markdown
---
theme: default
title: 자율주행 데일리 리포트 YYYY-MM-DD
info: 핵심 주제 한 줄 (예: Uber 자율주행 책임자 교체 예정)
fonts:
  sans: Noto Sans CJK KR
---
```

- `info`는 40자 안팎의 명사형 한 줄. 날짜를 넣지 않습니다.
- 신규 사항이 없는 날은 `info: 주요 신규 업데이트 없음`으로 적습니다. 이 문구가 그대로 분류 `신규 없음`의 기준이 됩니다.

## 3. 본문 구성

`---` 한 줄이 슬라이드 구분자입니다. 섹션 순서와 제목을 아래와 같이 고정합니다.

```markdown
# Executive Summary
## YYYY-MM-DD · {info와 같은 문구}

- **[신규] 기업명**: 무엇이 언제 보도·발표됐는지 한 문장. 단계(계획/시험/상용/무인)를 명시. [R1–R3]
- **운영 변화와 구분**: 이번 소식이 조직/계획/실행 중 무엇인지. 확인되지 않은 것도 적는다.
- **지정 기업**: Avride·Bolt·Mobileye·카카오모빌리티·쏘카 점검 결과 한 줄. [R5–R9]
- **May Mobility [중복]**: 신규 확인 사항 여부와 이전 보고 날짜. [R10–R13]

확인 기준: YYYY-MM-DD 한국시간 아침. 이전 발송본과 비교해 동일 사건·수치의 재보도를 제외했다.

---

# 주요 신규 업데이트
## [신규] 사건 제목

- **보도일**: YYYY-MM-DD. **예정일/시행일**: YYYY-MM-DD (있을 때만).
- **당사자**: 기업·인물·지역.
- 사실 한 문장마다 출처 번호. [R1]
- 이 사실로 추정하지 않는 것(계약 해지, 출시 지연 등)을 한 줄로 명시.

출처: [매체, 날짜][R1] · [매체, 날짜][R2]

---

# 기업/지역별 상세 내용
## 기업명 소제목

- 유료 원문을 못 열었으면 **[유료 기사][원문 미확인]** 표시 후 보완 출처를 적는다.
- **아직 확인되지 않은 것**: 신규 운행 허가, 안전요원 제거, 추가 차량 투입 등.
```

## 4. 표기 규칙

| 표기 | 뜻 | 위치 |
| --- | --- | --- |
| `[신규]` | 이번 리포트에서 처음 확인한 사실 | 불릿·소제목 앞 |
| `[중복]` | 이전 리포트에서 다룬 내용의 재점검 | May Mobility와 재등장 항목 |
| `[중복·추가 확인]` | 이전 내용에 새 근거가 붙은 경우 | 위와 같음 |
| `[유료 기사][원문 미확인]` | 원문을 직접 열지 못하고 검색 요약·보완 출처로 확인 | 상세 내용 |
| `[R숫자]` | 출처 번호. 본문 문장 끝에 붙이고 Reference에 같은 번호로 URL | 전체 |

- 계획과 실행을 문장에서 구분합니다. "발표했다", "예정이다", "개시했다", "허가받았다"를 섞지 않습니다.
- 안전요원 동승 시험과 안전요원 없는 운행, 운전자 보조(L2·L3)와 L4 사업 변화를 구분합니다.
- 전망·평가·가치 판단은 쓰지 않습니다. 공개 자료로 확인된 사실만 씁니다.
- 기업 이름은 `data/companies.json`의 표기를 그대로 씁니다(예: `카카오모빌리티`, `May Mobility`, `Pony.ai`). 다른 표기를 쓰면 기업 태그에 잡히지 않습니다.
- 메일 주소, 메시지 ID, 메일 본문, 개인 정보는 넣지 않습니다. 저장소는 공개입니다.

## 5. 게시 파이프라인이 자동으로 뽑아내는 것

MD만 올바르면 아래는 손댈 필요가 없습니다.

| 항목 | 출처 |
| --- | --- |
| 리포트 ID·날짜 | 폴더 이름 |
| 제목 | 머리말 `info` |
| 요약 | 본문에서 URL이 없고 25자를 넘는 첫 두 불릿 |
| 기업 태그 | `data/companies.json` 목록과 본문 대조. 단 "신규 확인 사항 없음" 같은 점검 줄, 출처·Reference 목록, URL에만 나온 기업은 제외 |
| 분류 | `info`가 "주요 신규 업데이트 없음"이면 `신규 없음`, 아니면 `동향` |
| 출처 목록 | 본문의 모든 `https://` 주소 (중복 제거) |
| 타임라인 `보고일` 항목 | 자동 추가 |
| 첨부 SHA-256 | 자동 계산 |

**자동으로 만들지 않는 것**: 타임라인의 사건(`events`)과 관계 그래프의 선(`relations`). 근거 문장·출처·리포트 ID가 있어야 하므로 게시자가 `data/catalog.json`에 직접 넣습니다. 형식은 [데이터 계약](DATA_CONTRACT.md)을 따릅니다.

## 6. 올리기 전 점검

1. 폴더 이름과 파일 이름의 날짜가 같다.
2. 머리말에 `info`가 있고 날짜가 들어 있지 않다.
3. 본문의 모든 `[R숫자]`가 Reference에 있고 URL이 `https://`로 시작한다.
4. 지정 6개사 표와 May Mobility 섹션이 있다. 신규가 없어도 "신규 확인 사항 없음"으로 채운다.
5. 기업 이름 표기가 `data/companies.json`과 같다.
6. 08:00 KST 전에 `main`에 push한다.
